# Skill: GitHub Action Integration

## When to use

Use this skill when the user wants to:
- add `go-sdk-generator` to a GitHub Actions workflow
- install a released version of the tool in CI
- dogfood one of the generated subcommand actions from this repository
- run `go-sdk-generator` commands without building the CLI from source

Prefer the actions when one of them already represents the workflow step that needs to be run.
Prefer `actions/install-tool` when the workflow only needs the tool to be available for later shell commands, loops, or more complex parallel orchestration.
When workflows prefer containerised execution, reproducible builds, or avoiding local installation entirely, published OCI images from `ghcr.io/arm-debug/go-sdk-generator` are also an option.


---

## Available Actions

Actions in this repository:
- `actions/install-tool` installs `go-sdk-generator`
- `actions/generate` runs `go-sdk-generator generate`

Example published action:

```yaml
uses: Arm-Debug/go-sdk-generator/actions/install-tool@v0
```

Example local path:

```yaml
uses: ./actions/install-tool
```

## What The Actions Do

Every action:
- resolves the release version from the action ref
- downloads the matching GitHub Release assets using `gh`
- installs the tool natively on Linux when a supported package manager is available
- otherwise extracts the released archive into the requested working directory
- verifies the installation with `--version`

The dedicated install action stops there.

Each command action additionally:
- runs a fixed `go-sdk-generator` subcommand using structured action inputs

## Shared Inputs

Every action exposes:
- `action-repo`
- `action-ref`
- `workdir`

Every action also exposes:
- the `cmd` output: a reference to the installed `go-sdk-generator` command for later workflow steps

The install action exposes no CLI-specific inputs.

Each command action also exposes one input per non-hidden CLI flag for its subcommand, including repeated root inputs shared across commands.

Commands that support positional operands also expose an `operands` input, with one operand per line.

## Version Resolution

The version of the tool follows the GitHub Action ref.

Rules:
- `@v0.29.0` installs exactly `v0.29.0`
- `@v0.29` installs the latest `v0.29.x` release
- `@v0` installs the latest `v0.x.y` release
- `@latest` installs the latest release binary
- branch names and commit SHAs build the CLI from source at that ref
- no action ref falls back to the latest release

If no release exists yet:
- the action prints that the tool has not been officially released yet
- the action does not fail
- installation and execution are skipped

## Platform Behaviour

### Linux

The action prefers native packages when available on the machine:
- `.deb` via `dpkg`
- `.rpm` via `rpm`
- `.apk` via `apk`

If none of those package managers are available, it falls back to the release archive.

### macOS

The action installs from the released archive.

### Windows

The action installs from the released archive.

## Integration Guidance

- Prefer subcommand actions when the workflow step is already fully defined by that action
- Prefer `actions/install-tool` when the goal is only to obtain the tool for later workflow steps
- `actions/install-tool` is the right fit when later steps need to loop, pipe output, run custom shell processing, or call a script that expects `go-sdk-generator` to already be available in the environment
- This matches the model used by other tool-installing actions such as `goreleaser/goreleaser-action` with `install-only` and `anchore/sbom-action/download-syft`
- Prefer the local action path when validating changes to the action in this repository
- Prefer `@v<major>` when consumers want automatic patch and minor updates within a major series
- Prefer exact tags when builds must be strictly reproducible
- Use `actions/install-tool` when later steps need to call the binary directly
- Keep `workdir` explicit when command inputs depend on relative paths
- Do not build the CLI from source in CI when the intent is to validate released artefacts
- Prefer OCI images from `ghcr.io/arm-debug/go-sdk-generator` when the workflow wants containerised execution instead of installing the binary onto the runner
