### Logging And Annotations

CLIs expose separate runtime configuration for normal logging and structured annotations.

CLI defaults:

- `logger=console`
- `annotation=none`

Action defaults:

- `logger=rich`
- `annotation=github`


Logger modes:

- `console`: use the standard generated console logger.
- `rich`: use a richer terminal logger built with [Charmbracelet Log](https://github.com/charmbracelet/log).
- `file`: write normal logs to the path selected by `logger_file`.
- `none`: disable normal log output.
- `custom`: use the logger implementation registered by the application during initialisation.

Annotation modes:

- Annotations are structured status messages separate from normal logs. They are primarily intended for CI systems that can render errors, warnings, and notices with extra context.
- `github`: emit GitHub Actions-compatible structured annotations using `golang-utils` annotation support.
- `none`: disable structured annotation output.

Logging and annotations are independent concerns. For example:

- `logger=rich` with `annotation=none` gives richer human-readable terminal logging without CI annotations.
- `logger=rich` with `annotation=github` gives richer terminal logging together with GitHub-compatible annotations.
- `logger=none` with `annotation=github` suppresses normal logs while still allowing advanced GitHub annotations.

### Custom Logger Registration

To use `logger=custom`, register `CustomLoggerDefinition` during application initialisation.

Add a file under `cmd/generator/` in package `generator`.

```go
package generator

import (
	"log/slog"
	"os"

	baselogs "github.com/ARM-software/golang-utils/utils/logs"
)

func init() {
	logger, err := baselogs.NewSlogLogger(slog.New(slog.NewJSONHandler(os.Stderr, nil)), "go-sdk-generator")
	if err != nil {
		panic(err)
	}
	CustomLoggerDefinition = logger
}
```

The command-line user does not supply an arbitrary Go implementation through the CLI.
Selecting `logger=custom` simply chooses the implementation already registered by the application.

If `logger=custom` is selected without registering `CustomLoggerDefinition`, the generated CLI returns an error.

### OCI Images

OCI images are also published to `ghcr.io/arm-debug/go-sdk-generator` for CI integration, reproducible builds, and workflows that prefer not to install the tool locally.

GitHub documents container-registry authentication and package permissions at:
`https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry`

On a local machine, if the package is not publicly accessible to the user's
account yet, log in to `ghcr.io` first. With the GitHub CLI installed and
already authenticated:

```sh
gh auth token | docker login ghcr.io -u "$(gh api user --jq .login)" --password-stdin
```

If `docker run` or `docker pull` fails with `403 Forbidden`, the GitHub
credentials usually do not have package-read access. The `read:packages`
permission is required, including in CI workflows that need to pull the OCI
image. For local-machine use with GitHub CLI credentials, refresh GitHub CLI
credentials, then log in to GHCR again:

```sh
docker logout ghcr.io
gh auth refresh --scopes read:packages
gh auth token | docker login ghcr.io -u "$(gh api user --jq .login)" --password-stdin
```

## GitHub Action

GitHub Actions are also published so that `go-sdk-generator` subcommands can be used easily in CI workflows.

Prefer using the actions directly when they already represent one complete workflow step.
Prefer the installation action when the goal is only to obtain the tool for later workflow steps, for example when a later step needs to loop, pipe output, perform additional shell processing, or call a script that expects the tool to already be available in the environment.
This follows the same general model used by tool-installing actions such as `goreleaser/goreleaser-action` with `install-only` and `anchore/sbom-action/download-syft`.

Actions in this repository:
- `actions/install-tool` installs `go-sdk-generator`
- `actions/generate` runs `go-sdk-generator generate`

Use the published installation action to obtain the tool so it can be used in other workflow steps:

```yaml
- name: Install go-sdk-generator from release

```


Use the published action from an official release to perform a particular action [`generate`] directly:

```yaml
- name: Run go-sdk-generator generate
  uses: Arm-Debug/go-sdk-generator/actions/generate@v0
  with:
    # provide the inputs required by the `generate` command here
```


The actions expose inputs for selecting the release source and installation location.
For actions that perform a particular subcommand, the remaining inputs map onto that subcommand's CLI flags.
Every action also exposes the `cmd` output, which resolves to a usable reference for the installed `go-sdk-generator` command in later workflow steps.

Inputs:
- `action-repo`: repository to download releases from; defaults to the repository running the action
- `workdir`: working directory where the CLI is run. If later workflow steps need to call the installed tool, use the `cmd` output rather than inferring its location from this directory.
- `actions/install-tool` exposes only installation inputs
- each action other than the installation one also exposes one input per non-hidden CLI flag for that subcommand, including repeated root inputs shared across commands
- commands with positional operands also expose an `operands` input, one operand per line

Outputs:
- `cmd` output: a reference to the installed `go-sdk-generator` command for later workflow steps

The action resolves official releases from the action version:
- `@v0.29.0` installs exactly `v0.29.0`
- `@v0.29` installs the latest `v0.29.x` release
- `@v0` installs the latest `v0.x.y` release
- `@latest` installs the latest released version
